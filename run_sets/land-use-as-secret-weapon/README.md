# land-use-as-secret-weapon

Run from the repo root (`M:\GitHub\WF-TDM-Runs`), with `pip install -e .` /
`uv run` set up.

## File structure

```
run_sets/land-use-as-secret-weapon/
├── README.md                       ← this file
├── run_set.yaml                    ← shared config: tdm_ref, baseline_control_center,
│                                      run_set-level overrides (vizToolDir, MasterPrefix),
│                                      outputs.include selection + size ceiling
├── scenarios/
│   └── <scenario_id>.yaml          ← one file per scenario; scenario_id + description +
│                                      scenario-level overrides, layered on top of
│                                      run_set.yaml's overrides at run time
└── inputs/
    ├── SE_2040_Base.csv             ← combined WFRC+MAG SE forecast (see "Prep inputs" below)
    ├── WFv1000_MasterNet_20260430.net   ← master highway network (Cube Voyager binary),
    │                                      a copy made for this run set so it can be
    │                                      edited without touching the tdm/ submodule
    ├── WFv1000_MasterNet_20260430.VPR   ← that network's Cube Voyager project file
    ├── Transit_Lin_2042/             ← transit line files + PT parameters, 2042 vintage
    │   ├── *.lin                      ← route line files, one per operator/mode group
    │   ├── Readlines.block            ← Cube block that READs every .lin file in this folder
    │   ├── Scenario_hand_coded_*.NTL  ← hand-coded drive/walk access links
    │   └── PT_Parameter/              ← fare (.FAR), mode-choice factor (.FAC), system (.PTS) files
    └── _input-prep/
        ├── prepare-se-2040-base.py   ← generates inputs/SE_2040_Base.csv
        └── data/                      ← raw WFRC_SE / MAG_SE source CSVs the script reads
```

Curated run outputs + `run_metadata.json` live outside this folder, under
`runs/land-use-as-secret-weapon/<scenario_id>/<run_id>/` (committed); raw,
gitignored model outputs live under the `tdm/` submodule's `Scenarios/`
working folder. See the framework's top-level `CLAUDE.md` for that layout.


## Editing this run set

### Add a new scenario

1. Copy `scenarios/lusw-base.yaml` to `scenarios/<new-scenario-id>.yaml` (or
   start from scratch). `scenario_id` must be unique within the run set,
   match `^[A-Za-z0-9][A-Za-z0-9_-]*$`, and never be reused after a scenario
   is retired — it's also the CLI's `--scenario` value and the Control
   Center's `ScenarioName` unless overridden.
2. Give it a short `description`.
3. Under `overrides:`, at minimum decide this scenario's SE forecast
   (`WFRC_SEFile`/`MAG_SEFile`), network coding (`LNfield`/`FTfield`), and
   transit (`Mlin`) — see the sections below for what values are valid and
   when you need to create new ones rather than reusing lusw-base's.
4. `uv run tdmruns validate-config --run-set land-use-as-secret-weapon` —
   confirms every override key exists on the baseline Control Center
   (`_ControlCenter - LUSW-Base_2040.block`) before anything is run.
5. `uv run tdmruns run-scenario --run-set land-use-as-secret-weapon --scenario <new-scenario-id>`.

### Edit SE data (create a copy, or bring in an SE file from elsewhere)

Each scenario's `WFRC_SEFile`/`MAG_SEFile` overrides point at the SE
(socioeconomic — households/employment by TAZ) CSV it runs against.
`inputs/SE_2040_Base.csv` is what `lusw-base` uses — generated by
`prepare-se-2040-base.py` from the raw WFRC/MAG source data (see "Prep
inputs" above), not hand-edited directly. A scenario testing a land-use
shift needs its own SE file, gotten one of two ways:

- **Copy and hand-edit.** Copy `inputs/SE_2040_Base.csv` to a new file under
  `inputs/` (e.g. `inputs/SE_2040_<description>.csv`) and edit the
  households/employment values for the TAZIDs this scenario shifts. Keep
  every TAZID row present, even unedited ones — the model expects a
  complete SE file, not a sparse override.
- **Bring in an SE file from another process.** If the land-use shift was
  produced elsewhere (a separate land-use model run, a GIS exercise, a file
  someone hands you), drop the finished CSV straight into `inputs/` — it
  just needs the same column structure/`;TAZID` key as
  `inputs/SE_2040_Base.csv`. Nothing about the override mechanism cares
  where the file came from.

Either way, point the scenario at it:

1. In the scenario's YAML, set `WFRC_SEFile`/`MAG_SEFile` to the new file's
   path, e.g.
   `'..\..\..\run_sets\land-use-as-secret-weapon\inputs\SE_2040_<description>.csv'`
   — single-quoted, same `..\..\..\` climb-back-to-repo-root convention as
   `MasterPrefix`/`Mlin` (see "Update override variables" below for why the
   quoting matters).
2. Re-run `validate-config`, then the scenario.

### Edit the master network (creating new LN & FT fields)

`run_set.yaml`'s `MasterPrefix` override points every scenario in this run
set at one shared master network — `inputs/WFv1000_MasterNet_20260430`, a
copy of the TDM's master network made specifically for this run set so it
can be edited without touching the `tdm/` submodule. Rather than a separate
`.net` file per scenario, each scenario instead selects a pair of *fields*
on that one shared network: `LNfield` (lane count) and `FTfield`
(functional type).

Existing fields follow the naming convention
`<LN|FT><base year, 2 digits>_<horizon year, 2 digits>` — e.g. `LN23_42` /
`FT23_42` is the 2023-base, 2042-horizon coding `lusw-base` uses (there are
also `..._32`/`..._50` fields already on the network for other horizons).
To code up a new lane/functional-type configuration for a scenario:

1. Open `inputs/WFv1000_MasterNet_20260430.net` in Cube Voyager — this is
   the network file.
2. In the network file, add new `LN##_##` / `FT##_##` fields to the link
   layer — typically by copying the nearest-matching existing field (e.g.
   `LN23_42`/`FT23_42`) and then editing values only for the links this
   scenario changes.
3. Save the network back to `WFv1000_MasterNet_20260430.net`. Every
   scenario referencing `MasterPrefix` shares this one file, so this edit
   is visible to all of them — only the field *name* each scenario selects
   differs.
4. In the new/edited scenario's YAML, set `LNfield`/`FTfield` to the new
   field names.
5. Re-run `validate-config`. It only checks that `LNfield`/`FTfield` are
   valid Control Center *keys* — it can't confirm the field name you gave
   them actually exists on the network. A typo'd field name will only
   surface as a Cube Voyager error at run time, so double-check the field
   exists in the `.net` file first.

### Edit transit (create a copy of the current Lin directory)

Each scenario's `Mlin` override points at a folder (relative path, trailing
`\`) holding that scenario's full transit line-file set: `.lin` route
files, `Readlines.block` (the Cube block that `READ`s every `.lin` file in
the folder), `.NTL` hand-coded-link files, and the `PT_Parameter/`
fare/factor/system files. `inputs/Transit_Lin_2042/` is what `lusw-base`
uses today.

Transit isn't edited in place — a scenario that changes transit gets its
**own copy of the whole folder**, so scenarios that don't touch transit
keep working against the original, unedited one:

1. Copy `inputs/Transit_Lin_2042/` to a new folder under `inputs/`, e.g.
   `inputs/Transit_Lin_<description>/`.
2. Edit the `.lin` files (and `.NTL` / `PT_Parameter/*` if needed) in the
   copy. `Readlines.block` only needs editing if you add/remove/rename a
   `.lin` file.
3. In the scenario's YAML, set `Mlin` to the new folder, e.g.
   `'..\..\..\run_sets\land-use-as-secret-weapon\inputs\Transit_Lin_<description>\'`
   — keep the trailing backslash and the `..\..\..\` prefix (it climbs back
   out of the TDM's fixed `1_Inputs\4_Transit\` prefix to this repo's root —
   the same relative-path trick `WFRC_SEFile`/`MAG_SEFile`/`MasterPrefix`
   use).
4. Re-run `validate-config`, then the scenario. This won't validate the transit line
   files against the network fields for scenario, so that will have to be done
   separately or it will crash in model stream and fix and rerun will need to be
   done.

### Add or change which outputs get curated

`run_set.yaml`'s `outputs:` block decides what gets copied out of a raw
model run into `runs/land-use-as-secret-weapon/<scenario_id>/<run_id>/outputs/`
after each run — everything else in the scenario folder stays on disk,
gitignored, and is never pushed. A scenario can also declare its own
`outputs:` block to override the run set's for just that scenario.

`outputs.include` is a list of entries, each one of three types:

- **`datafile`** — a glob matched against the scenario folder (e.g.
  `"4_ModeChoice/4_Shares/*Shares_Summary_long.csv"`). Add an optional
  `columns: [...]` list to keep only those columns (matched against the
  CSV's header row); the matched file is then written as
  `<stem>_filtered.csv` instead of copied byte-for-byte — this run set uses
  it on `*ZoneSummary_TripsByMode.csv` and `*Summary_SEGID.csv`, both of
  which are far wider than what the reports actually read. Omit `columns`
  to copy the file as-is.
- **`matrix`** — a glob matched against a Cube `.mtx` file, plus a required
  `tabs: [...]` list of table/core names to extract (only those tables are
  kept, not the whole matrix). Optional `format:` is `omx` (default —
  readable directly in Python via the `openmatrix` package) or `mtx`
  (converted back to Cube's native TPP format via `CONVERTMAT`, for when
  the curated output needs to be read by Voyager itself). Requires Voyager
  to be available at curation time (`config/local.yaml`'s `Voyager_EXE`).
  Not currently used in this run set, but available if a scenario needs
  skim output curated.
- **`network`** — a glob matched against a Cube `.net` file, plus a
  required `fields: [...]` list of link attributes to keep (plus geometry).
  Optional `format:` is `geojson` (default — reprojected to EPSG:4326,
  readable via `geopandas`), `shp` (zipped Esri shapefile, native CRS), or
  `net` (Cube's own native format, field-filtered). Also requires Voyager
  at curation time. Not currently used in this run set.

`max_file_size_mb` (currently `95` here) is a hard per-file ceiling —
curation refuses a matched file over that size. Set below GitHub's 100 MB
hard limit to leave a little headroom.

To curate a new output: add an entry to `run_set.yaml`'s `outputs.include`
(or a scenario's own `outputs:` block, if it's scenario-specific), run
`validate-config`, then re-run the scenario — curation only happens as part
of a run, there's no separate "re-curate" command for a run that already
completed.

### Update override variables in a scenario YAML

A scenario's `overrides:` block is layered on top of `run_set.yaml`'s own
`overrides:` (which apply to every scenario) — see "Config layer order" in
the framework's top-level `CLAUDE.md`. Any key used here must already exist
somewhere in the baseline Control Center
(`_ControlCenter - LUSW-Base_2040.block`), or `validate-config` rejects it
before anything runs. The keys this run set currently exercises:

| Key | Set at | Meaning |
|---|---|---|
| `vizToolDir` | run_set.yaml | Shared viz-tool output folder for the whole run set |
| `MasterPrefix` | run_set.yaml | Path (no `.net` extension) to the shared master network every scenario reads |
| `WFRC_SEFile` / `MAG_SEFile` | scenario | SE forecast CSV this scenario uses |
| `LNfield` / `FTfield` | scenario | Which lane-count / functional-type field on `MasterPrefix`'s network this scenario codes to |
| `Mlin` | scenario | Folder holding this scenario's transit line files |

Any other Control Center key is fair game too — there's exactly one
override mechanism, whether it's selecting an input file or tuning a model
parameter (see the framework's "one override mechanism" design note).
`WFRC_SEFile`/`MAG_SEFile`/`MasterPrefix`/`Mlin` are relative paths and must
stay **single-quoted** in YAML, not double-quoted — a double-quoted scalar
treats `\r`/`\n`/etc. inside the path as escape sequences, and every one of
these paths contains `..\run_sets\...`, where `\r` would otherwise be read
as a carriage-return escape and corrupt the path.


## Prep inputs (once, or whenever the source data changes)

```
uv run python run_sets/land-use-as-secret-weapon/inputs/_input-prep/prepare-se-2040-base.py
```

Writes `inputs/SE_2040_Base.csv` (WFRC 2040 data for TAZID 1-2216, MAG data
interpolated to 2040 for TAZID 2217-3562).

## Validate config

```
uv run tdmruns validate-config --run-set land-use-as-secret-weapon
```

Checks every scenario's override keys against the baseline before anything
is run. Run this after editing `run_set.yaml` or any scenario YAML.

## Sync the TDM submodule

```
uv run tdmruns sync-tdm --run-set land-use-as-secret-weapon
```

Checks out the submodule to this run_set's `tdm_ref`. Refuses on a dirty
submodule tree. `run-scenario`/`run-set` do this automatically, but useful
to run standalone first if you just want to confirm the ref resolves.

## Run one scenario

```
uv run tdmruns run-scenario --run-set land-use-as-secret-weapon --scenario lusw-base
```

Add `--force` to re-run a scenario that already has a successful recorded run.

## Run every scenario in the run set

```
uv run tdmruns run-set --run-set land-use-as-secret-weapon
```

## Check status

```
uv run tdmruns status
```

Shows the latest result per scenario across all run sets.

## Copy outputs only, without running the model

Not applicable here — this run set executes through the CLI
(`run-scenario`/`run-set`), which curates outputs automatically as part of
the run. `import-manual-run` / `import-manual-run-set` only apply to
scenarios run manually outside the CLI (see the framework's top-level
`CLAUDE.md`); use them only if a scenario here ever needs to be run that way
instead.

## Retiring this run set (once it's done and won't be re-run)

```
uv run tdmruns snapshot-run-set --run-set land-use-as-secret-weapon
uv run tdmruns purge-run-set-outputs --run-set land-use-as-secret-weapon
```

Only relevant once reports exist that read from `runs/` and the curated
outputs need to be trimmed down. See "Retiring a run set" in the top-level
`CLAUDE.md` before using this.
